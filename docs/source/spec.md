# Промпт для Claude Code: Telegram-бот оформления работ по ГОСТ

Как пользоваться этим промптом
Этот раздел для тебя, а всё, что ниже, — сам промпт для Claude Code. Подготовка занимает 10 минут:
1. Экспортируй этот документ в Markdown и сохрани в пустую папку проекта как SPEC.md.
2. Создай папку docs/source/ и положи туда: файл с описанием ГОСТа из твоего проекта, свой системный промпт, методичку своего вуза (PDF или DOCX).
3. Создай папку tests/corpus/raw/ и положи туда 15–30 реальных курсовых и рефератов, особенно кривых: с отступами пробелами, ручной нумерацией, жирным текстом вместо заголовков.
4. Запусти Claude Code в этой папке и напиши: «Прочитай SPEC.md и всё в docs/source/. Начни с этапа 0 и остановись после него».
Claude Code будет работать по этапам и останавливаться после каждого. Не пропускай проверку ядра на корпусе: от него зависит всё качество продукта.

## 1. Роль и цель

Ты — senior Python-разработчик. Строишь с нуля production-ready Telegram-бота, который оформляет документы Word (.docx) по выбранному профилю: ГОСТ 7.32-2017 или требования конкретного вуза. Меняется только оформление, текст остаётся тем же.

Бизнес-модель: пользователь бесплатно получает краткий отчёт по документу, платит через ЮKassa (СБП) и получает оформленный файл. Цена задаётся в конфиге (по умолчанию 300 ₽). Владелец — ИП, магазин ЮKassa уже подключён.

### Непреложные принципы

1. **Текст неприкосновенен.** Программа и ИИ меняют только форматирование. Допустимые изменения текста — короткий белый список (раздел 6), каждое попадает в отчёт. Если проверка целостности не прошла, файл не выдаётся.
2. **Идеально там, где система уверена, и честный отчёт там, где нет.** Каждый блок документа получает тип и уверенность. Неуверенное уточняется у ИИ, затем у пользователя, а остаток явно перечисляется в отчёте с указанием места.
3. **Программно в первую очередь.** ИИ вызывается только для неоднозначных абзацев, только для классификации (возвращает метки, а не текст) и с жёстким бюджетом на документ. Предварительный отчёт до оплаты не использует ИИ вообще.
4. **Профиль — это данные, а не код.** Новый вуз добавляется папкой с `profile.yaml` и `template.docx` без изменения кода.
5. **Источник истины по правилам оформления** — файлы в `docs/source/`. Если в этом промпте написано одно, а в файлах пользователя другое, побеждают файлы, а ты показываешь расхождение.
6. **Не выдумывай требования.** Если что-то неясно, спроси, а не угадывай. Работай по этапам из раздела 13 и останавливайся после каждого.

## 2. Пользовательский сценарий

Все тексты бота вынеси в `app/bot/texts.py`, чтобы их можно было править без изменения логики. Тон дружелюбный и короткий, на «вы».

1. **Первый запуск `/start`.** Приветствие в 2–3 строки: что делает бот, что меняется только оформление. Показываются ссылки на оферту, политику обработки ПДн и правила, кнопка «Принимаю условия». Без согласия дальше нельзя. Сохраняются время согласия и версия документов. При изменении версии документов согласие запрашивается снова.
2. **Главное меню.** Кнопки: «ГОСТ 7.32-2017», «<Название вуза>» (список профилей строится из папки `profiles/`), «Как это работает», «Документы и правила», «Поддержка».
3. **Выбор профиля** → «Пришлите файл .docx (до 20 МБ)».
4. **Приём файла и валидация.** Отклонять с понятным объяснением: не .docx (для .doc — инструкция «Файл → Сохранить как → .docx»), .docm, файл больше 20 МБ (лимит скачивания Bot API), повреждённый или зашифрованный файл, документ с непринятыми исправлениями (попросить принять или отклонить их в Word). Пока идёт анализ, показывать статус «Анализирую документ…».
5. **Бесплатный отчёт (без ИИ).** Формат примерно такой:
   - профиль; примерный объём в страницах;
   - найдено: заголовков по уровням, таблиц, рисунков, формул, источников в списке литературы, приложений;
   - найдено нарушений оформления по категориям (шрифт, интервалы, отступы, поля, подписи, заголовки, нумерация страниц);
   - «требуют уточнения: N элементов — уточним после оплаты»;
   - цена. Кнопки: «Оплатить N ₽ (СБП)», «Другой профиль», «Отмена».
6. **Email для чека** (если в конфиге включены чеки): спрашивается один раз, валидируется, сохраняется. В меню есть кнопка «Изменить email».
7. **Оплата.** Бот создаёт платёж и присылает сообщение с URL-кнопкой «Перейти к оплате» и кнопкой «Я оплатил — проверить». Ссылка живёт 30 минут (настраивается), потом заказ переходит в `expired`.
8. **После оплаты** (по webhook или по кнопке проверки) → «Оплата получена, оформляю документ…» → задача ставится в очередь.
9. **Уточнения (если нужны).** Если после правил и ИИ остались неуверенные элементы, бот задаёт до 5 вопросов кнопками, по одному сообщению на вопрос: фрагмент текста (до 200 символов) и варианты «Заголовок 1 уровня / Заголовок 2 уровня / Обычный текст / Подпись рисунка / …». Если пользователь не ответил за 30 минут, берётся лучший вариант с пометкой в отчёте.
10. **Результат.** Бот присылает оформленный .docx (имя: `<исходное имя>_ГОСТ.docx`) и итоговый отчёт: что исправлено, какие текстовые нормализации сделаны, что стоит проверить вручную с указанием раздела и первых слов абзаца. Кнопки: «Всё отлично», «Что-то не так». Затем снова главное меню.
11. **«Что-то не так».** Пользователь описывает проблему текстом. Бот спрашивает разрешение сохранить файл на 14 дней для разбора. Заказ получает статус `complaint` и уведомление владельцу. Одна бесплатная повторная обработка того же документа.
12. **Ошибка после оплаты** (проверка целостности или линтер не прошли, упал worker). Бот не отправляет сломанный файл, пишет пользователю «Не удалось оформить документ автоматически, деньги вернутся в течение…», делает автоматический возврат через API ЮKassa и уведомляет владельца.

### Служебное

- `/admin` (только для `ADMIN_IDS`): статистика за день/неделю, последние заказы, заказы с ошибками и жалобами, ручной возврат по id заказа, режим беты.
- **Режим беты** (флаг в конфиге): для пользователей из белого списка оплата пропускается, остальной сценарий тот же.
- Защита от спама: не больше 10 документов в час на пользователя. Если тот же файл (по хешу) с тем же профилем уже оплачен за последние 24 часа, результат выдаётся повторно бесплатно. Другой профиль — новый заказ.

## 3. Стек и структура проекта

- Python 3.12, менеджер зависимостей `uv` (или Poetry), строгая типизация, `ruff` + `mypy`.
- **Бот:** aiogram 3.x, FSM на Redis.
- **API для webhook и юридических страниц:** FastAPI + uvicorn.
- **Очередь задач:** arq (async, Redis). Анализ и оформление выполняются только в worker, никогда в процессе бота.
- **БД:** PostgreSQL 16, SQLAlchemy 2.x (async) + Alembic.
- **DOCX:** python-docx + lxml (большая часть работы — на уровне XML).
- **Рендер:** LibreOffice headless (обновление оглавления и полей, PDF для внутренних проверок).
- **Оплата:** официальный SDK `yookassa` или прямые HTTP-запросы через httpx.
- **ИИ:** Anthropic API через официальный SDK `anthropic`, модель задаётся в конфиге.
- **Конфиг:** pydantic-settings, все секреты в `.env`, в репозитории только `.env.example`.
- **Деплой:** Docker Compose, Caddy для HTTPS.

## 4. Ядро форматирования

Архитектура гибридная: **документ разбирается в промежуточное представление (IR), а результат собирается заново в копии исходного пакета .docx.** Копия пакета нужна, чтобы картинки, сноски, гиперссылки, формулы и встроенные объекты сохраняли свои связи (relationships). Всё оформление при этом строится с нуля из IR и профиля, а мусор исходника выбрасывается.

### 4.1 Конвейер

1. **Чтение и валидация пакета** (`docx_io.py`): проверка zip, защита от zip-бомбы (лимит распакованного размера, например 200 МБ), безопасный парсинг XML (`resolve_entities=False`, `no_network=True`), отказ при наличии `w:ins`/`w:del` (непринятые исправления) и макросов.
2. **Разбор в IR** (`parser.py`): обход `w:body` по порядку. Каждый абзац, таблица, разрыв раздела становится блоком. Для каждого абзаца вычисляется **эффективное** форматирование с учётом наследования: `docDefaults` → цепочка стилей (`basedOn`) → прямое форматирование абзаца → прямое форматирование run.
3. **Классификация** (раздел 5): каждому блоку присваивается тип и уверенность.
4. **Нормализация** (`normalize.py`): только операции из белого списка (раздел 6), каждая записывается в журнал изменений.
5. **Сборка** (`builder.py`): применение профиля.
6. **Рендер** (`render.py`): LibreOffice headless обновляет оглавление и поля, а также делает PDF для проверок.
7. **Проверка целостности** и **линтер** (раздел 6). Любая ошибка = файл не выдаётся.
8. **Отчёт** (`report.py`).

### 4.2 Модель IR

Типы блоков:

- `title_page` — титульный лист. Не трогается вообще, переносится как есть.
- `toc` — существующее оглавление. Удаляется и генерируется заново полем TOC.
- `structural_heading` — СОДЕРЖАНИЕ, ВВЕДЕНИЕ, ЗАКЛЮЧЕНИЕ, СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ, РЕФЕРАТ, ОПРЕДЕЛЕНИЯ, ОБОЗНАЧЕНИЯ И СОКРАЩЕНИЯ и т.п.
- `heading` с `level` 1–3 — заголовки разделов и подразделов.
- `appendix_heading` — «ПРИЛОЖЕНИЕ А» и его название.
- `body` — обычный абзац.
- `list_item` с `kind` (bullet/ordered) и `level`.
- `figure` — абзац с рисунком (`w:drawing`/`w:pict`), `figure_caption`.
- `table`, `table_caption`, `table_note`.
- `formula` — абзац с OMML (`m:oMath`/`m:oMathPara`), с номером или без.
- `bibliography_item`.
- `page_break`, `section_break` — структурные разрывы.
- `empty` — пустые абзацы, удаляются.
- `unknown` — всё, что не удалось определить, обязательно попадает в отчёт.

```python
class Run(BaseModel):
    text: str
    bold: bool = False
    italic: bool = False
    underline: bool = False
    superscript: bool = False
    subscript: bool = False
    strike: bool = False
    kind: Literal["text", "tab", "break", "footnote_ref", "hyperlink", "field", "drawing", "math", "other"] = "text"
    xml_ref: str | None = None   # ссылка на исходный элемент для непрозрачных run

class Block(BaseModel):
    id: str                      # стабильный id, напр. "p0042"
    type: BlockType
    level: int | None = None
    confidence: float            # 0..1
    source: Literal["rules", "llm", "user", "default"]
    runs: list[Run] = []
    xml_ref: str | None = None   # для таблиц, рисунков, формул, титульного листа
    features: dict[str, Any] = {}
    page_estimate: int | None = None
    notes: list[str] = []        # что попадёт в отчёт
```

### 4.3 Профиль

Профиль — папка с `profile.yaml`, `template.docx` и `README.md` (источник требований). `template.docx` содержит все нужные стили с правильными параметрами и колонтитулы с номером страницы. Набор стилей фиксирован, имена стилей одинаковы во всех профилях: `GostBody`, `GostHeading1..3`, `GostStructHeading`, `GostAppendixHeading`, `GostListBullet`, `GostListNumber`, `GostFigure`, `GostFigureCaption`, `GostTableCaption`, `GostTableText`, `GostTableNote`, `GostFormula`, `GostBibItem`, `GostTOC1..3`. Генерируй `template.docx` скриптом из `profile.yaml` (`python -m app.core.cli build-template <profile>`), а не вручную, чтобы YAML оставался единственным источником.

Стартовые значения для ГОСТ 7.32-2017 — **ориентир**. Сверь каждое с файлами в `docs/source/` и покажи таблицу расхождений до того, как писать код:

### 4.4 Сборка

1. Скопировать исходный пакет. Заменить `styles.xml` стилями из `template.docx` профиля, сохранив только те исходные стили, на которые ссылаются непрозрачные блоки (таблицы, титульный лист), с переименованием при конфликте.
2. Заменить параметры страницы (`w:sectPr`) и колонтитулы по профилю. Титульный лист: номер страницы не показывается (отдельный раздел или `titlePg`), но страница считается.
3. Пересобрать `w:body` из IR. Для каждого текстового блока создаётся новый `w:p` со ссылкой на стиль профиля **без прямого форматирования абзаца**. Run переносятся с текстом и только семантическими признаками: bold, italic, underline, sup/sub, strike. Шрифт, кегль, цвет, выделение и прочее из run удаляются.
4. Непрозрачные элементы (`w:drawing`, `m:oMath`, сноски, гиперссылки, поля, закладки) переносятся как XML-узлы с сохранением `r:id`, ведь пакет тот же.
5. Таблицы переносятся целиком, но к тексту в ячейках применяется `GostTableText`, а ширина таблицы ограничивается шириной поля набора. Структура таблиц (объединения, границы) не меняется.
6. Заголовки: ручная нумерация («1.», «1.2.») нормализуется по шаблону профиля в текст. Автоматическая многоуровневая нумерация Word на MVP не используется, это надёжнее. Для новых страниц используется `pageBreakBefore` в стиле, а не пустые абзацы.
7. Подписи рисунков и таблиц нормализуются по шаблону («Рис. 3. Схема» → «Рисунок 3 – Схема»). Номера пересчитываются по порядку только если в профиле `numbering: continuous` и исходная нумерация последовательная. Если в исходнике есть пропуски или дубли, номера не меняются, а проблема попадает в отчёт: иначе сломаются ссылки в тексте («см. рисунок 3»).
8. Оглавление: удалить старое, вставить поле `TOC \o "1-3" \h \z \u` после титульного листа, выставить `w:updateFields` в `settings.xml` и обновить поля через LibreOffice.
9. Пустые абзацы удаляются. Отступы, сделанные пробелами и табуляцией в начале абзаца, удаляются. Двойные пробелы схлопываются (это нормализация из белого списка).

**Важно про LibreOffice:** пагинация в LibreOffice может немного отличаться от Word, поэтому номера страниц в оглавлении могут расходиться на ±1. Установи в образ worker шрифты Times New Roman (`ttf-mscorefonts-installer`) с метрически совместимым Liberation Serif как запасным вариантом. Проверь на корпусе, насколько оглавление совпадает с Word, и опиши результат.

## 5. Классификация блоков

Классификация идёт в три слоя: правила → ИИ → пользователь. Каждый следующий слой получает только то, что не решил предыдущий.

### 5.1 Признаки (`features.py`)

Для каждого абзаца: имя стиля и `outlineLvl` (Heading N / Заголовок N), паттерн номера в начале (`^\d+(\.\d+)*\.?\s`), длина в символах и словах, точка в конце, доля заглавных букв, доля жирного, выравнивание, кегль относительно медианного кегля документа, наличие рисунка/формулы/поля, соседние блоки (что до и после: таблица, рисунок, заголовок), позиция в документе (до первого «СОДЕРЖАНИЕ»/«ВВЕДЕНИЕ», внутри списка литературы, внутри приложения), маркеры списка (Word numbering, «–», «•», «а)», «1)»).

### 5.2 Правила (`rules.py`)

Каждое правило — маленькая функция, которая голосует за тип с весом. Уверенность = нормализованная разница между лучшим и вторым вариантом. Обязательные правила:

- **Титульный лист:** всё до первого структурного заголовка (СОДЕРЖАНИЕ, ВВЕДЕНИЕ, РЕФЕРАТ и т.п.) или до первого разрыва страницы/раздела на первой странице.
- **Структурные заголовки:** словарь с вариантами написания («Список литературы», «Список использованных источников», «Библиографический список», «Оглавление» → СОДЕРЖАНИЕ) с учётом регистра, пробелов и точки в конце.
- **Приложения:** `^ПРИЛОЖЕНИЕ\s+[А-Я]` и вариации.
- **Заголовки с номером:** номер + короткая строка (до \~150 символов) без точки в конце → `heading` с уровнем по глубине номера. Стиль Heading N повышает уверенность.
- **Заголовки без номера:** жирный/крупный короткий абзац, отдельно стоящий, за которым идёт обычный текст, — средняя уверенность.
- **Подписи:** `^(Рисунок|Рис\.?)\s*\d+` рядом с рисунком; `^Таблица\s*\d+` перед таблицей; «Продолжение таблицы».
- **Список литературы:** нумерованные абзацы после соответствующего структурного заголовка и до следующего.
- **Списки:** Word numbering или текстовые маркеры.
- **Формулы:** абзац, состоящий из OMML (+ необязательный номер в скобках).

Пороги в конфиге: уверенность ≥ 0.90 — принять; 0.60–0.90 — отправить в ИИ; < 0.60 или противоречие правил и ИИ — спросить пользователя.

### 5.3 ИИ (`llm.py`)

- Вызывается **только после оплаты** и только для блоков из «серой зоны». Предварительный отчёт до оплаты работает без ИИ: неуверенные элементы там только считаются.
- **Один запрос на документ**, все неоднозначные блоки сразу. Если их больше лимита (например, 60), остальные идут к пользователю или помечаются в отчёте.
- В запрос идут: id блока, его текст (обрезанный до 300 символов), признаки, краткий контекст (тип и первые 80 символов соседних блоков). **Титульный лист не отправляется никогда.** Email, телефоны и ФИО-подобные строки маскируются регуляркой.
- Ответ строго в JSON: `[{"id": "p0042", "type": "heading", "level": 2, "confidence": 0.8}]`. Ответ валидируется pydantic. Неизвестные id и типы отбрасываются, текста в ответе быть не должно, а если он есть, он игнорируется.
- Системный промпт лежит в `app/prompts/classifier_system.md`. Возьми за основу системный промпт пользователя из `docs/source/` и адаптируй его под задачу классификации.
- Модель задаётся в конфиге: `LLM_MODEL=claude-haiku-5-5` по умолчанию, `LLM_ESCALATION_MODEL=claude-sonnet-5-5` для повторного запроса, если ответ невалиден. Сверь актуальные имена моделей и цены в документации Anthropic перед реализацией.
- Жёсткие лимиты: таймаут 60 с, 1 повтор, `max_tokens` по размеру батча, лимит стоимости на документ в конфиге. Логируй токены и стоимость каждого вызова в БД.
- Флаг `LLM_ENABLED`. Если ИИ выключен или недоступен, серая зона уходит пользователю, а затем в отчёт. Обработка не падает.

### 5.4 Вопросы пользователю (`resolve.py`)

Не больше 5 вопросов на документ, отсортированных по важности (заголовки важнее подписей, подписи важнее списков). Пока worker ждёт ответа, заказ имеет статус `awaiting_user_input`, задача сохраняет IR в БД и завершается, а после ответа или таймаута ставится новая задача «продолжить сборку».

## 6. Контроль качества

Файл выдаётся пользователю, только если прошли обе проверки: целостность текста и линтер. Это и есть гарантия «идеально там, где уверены».

### 6.1 Белый список текстовых нормализаций (`normalize.py`)

Только эти изменения текста разрешены. Каждое записывается в журнал (id блока, было → стало) и попадает в итоговый отчёт сводкой:

1. Удаление пробелов и табуляций в начале и конце абзаца.
2. Схлопывание нескольких пробелов в один.
3. Удаление пустых абзацев.
4. Нормализация номера заголовка по шаблону профиля («1.2. Название» → «1.2 Название»), удаление точки в конце заголовка.
5. Изменение регистра структурных заголовков («Введение» → «ВВЕДЕНИЕ»), если этого требует профиль.
6. Нормализация префикса подписи («Рис. 3.» → «Рисунок 3 –», «Таблица 2.» → «Таблица 2 –»), тире между номером и названием.
7. Перенумерация рисунков и таблиц — только по условию из раздела 4.4 (п. 7).
8. Замена старого оглавления новым полем TOC.

Всё остальное — орфографию, кавычки, дефисы внутри текста, сокращения — не трогать.

### 6.2 Проверка целостности (`integrity.py`)

1. Из исходника извлекается последовательность слов (без титульного листа и оглавления, которые сравниваются отдельно: титульный лист побайтно по тексту, оглавление не сравнивается).
2. К ней применяются те же нормализации из журнала.
3. Из результата извлекается последовательность слов тем же способом.
4. Последовательности должны совпасть **полностью**. Также совпадают количество рисунков, таблиц, формул, сносок и гиперссылок.
5. При несовпадении — ошибка с диффом в лог (без текста документа в продовых логах: только id блоков и позиции), заказ в `failed`.

### 6.3 Линтер (`linter.py`)

Открывает **готовый** файл заново, вычисляет эффективное форматирование каждого абзаца и проверяет его против профиля. Это независимая проверка, а не повторный прогон кода сборки. Проверки:

- поля и размер страницы во всех разделах;
- шрифт, кегль, интервал, отступ первой строки, выравнивание для каждого типа блока;
- отсутствие прямого форматирования, противоречащего стилю;
- структурные заголовки и заголовки 1 уровня с новой страницы;
- отсутствие точки в конце заголовков;
- формат подписей рисунков и таблиц, их положение относительно объекта;
- нумерация страниц: есть, в нужном месте, не видна на титульном листе;
- оглавление существует и содержит все заголовки до нужного уровня;
- отсутствие пустых абзацев и двойных пробелов.

Результат: список `{rule, block_id, severity, message}`. Severity `error` блокирует выдачу, `warning` попадает в отчёт.

### 6.4 Отчёты (`report.py`)

**Предварительный (до оплаты):** счётчики найденных элементов и нарушений по категориям, число неуверенных элементов, цена. Строится только правилами, за 1–5 секунд.

**Итоговый (после оформления):** что исправлено (по категориям с числами), сделанные текстовые нормализации, ответы пользователя, а главное — блок «Проверьте вручную» с указанием раздела, типа и первых 8–10 слов каждого элемента, где система не была уверена. Формат: сообщение в Telegram до 4096 символов. Если не помещается, то короткое сообщение плюс отчёт отдельным .txt.

## 7. Оплата через ЮKassa (СБП)

Перед реализацией сверь все поля и эндпоинты с актуальной документацией ЮKassa (yookassa.ru/developers): ниже описана схема, а не окончательный контракт.

### 7.1 Создание платежа

`POST https://api.yookassa.ru/v3/payments`, Basic auth `shopId:secretKey`, заголовок `Idempotence-Key` = UUID, привязанный к заказу (сохраняется в БД, при повторной попытке используется тот же ключ).

```json
{
  "amount": {"value": "300.00", "currency": "RUB"},
  "payment_method_data": {"type": "sbp"},
  "confirmation": {"type": "redirect", "return_url": "https://t.me/<BOT_USERNAME>"},
  "capture": true,
  "description": "Оформление документа по ГОСТ, заказ <order_short_id>",
  "metadata": {"order_id": "<uuid>", "tg_user_id": "<id>"},
  "receipt": {
    "customer": {"email": "<email>"},
    "items": [{
      "description": "Услуга по оформлению документа",
      "quantity": "1.00",
      "amount": {"value": "300.00", "currency": "RUB"},
      "vat_code": 1,
      "payment_subject": "service",
      "payment_mode": "full_payment"
    }]
  }
}
```

Объект `receipt` добавляется только при `RECEIPTS_ENABLED=true`. Параметры чека (`vat_code`, налоговая система) задаются в конфиге и зависят от налогового режима ИП. Оставь в README пометку: владелец должен уточнить их у бухгалтера или в поддержке ЮKassa. Пользователю отправляется `confirmation.confirmation_url` URL-кнопкой.

### 7.2 Подтверждение оплаты

- **Webhook** `POST /webhooks/yookassa` в FastAPI. Обрабатываемые события: `payment.succeeded`, `payment.canceled`, `refund.succeeded`.
- **Тело webhook не является доказательством оплаты.** Получив уведомление, сделай `GET /v3/payments/{id}` и доверяй только ответу API: статус, сумма, валюта, `metadata.order_id`. Дополнительно проверяй IP отправителя по списку адресов ЮKassa из документации (список в конфиге).
- **Идемпотентность:** обработка в транзакции с блокировкой строки заказа (`SELECT … FOR UPDATE`). Переход `awaiting_payment → paid` возможен один раз. Повторный webhook возвращает 200 и ничего не делает. Задача оформления ставится в очередь с job\_id = order\_id, чтобы не было дублей.
- Webhook всегда быстро отвечает 200 после записи события. Тяжёлая работа выполняется в worker.
- **Подстраховка:** кнопка «Я оплатил — проверить» и фоновая задача раз в минуту проверяют через API заказы в `awaiting_payment` младше 2 часов. Это закрывает случай потерянного webhook.
- Истёкшие и отменённые платежи переводят заказ в `expired`/`canceled`. Пользователь может создать новый платёж из того же анализа, пока файл не удалён.

### 7.3 Возвраты

`POST /v3/refunds` с `payment_id`, суммой и своим `Idempotence-Key`. Автоматический возврат — при `failed` после оплаты (раздел 2, п. 12). Ручной — командой из `/admin`. Всё логируется в таблицу платежей.

### 7.4 Тестирование оплаты

Всё разрабатывается и проверяется в **тестовом магазине** ЮKassa (отдельные `shopId` и ключ). Переключение на боевой магазин — только сменой переменных окружения. Напиши интеграционные тесты на: успешную оплату, повтор webhook, потерянный webhook (подстраховка), отмену, возврат, поддельный webhook (несуществующий платёж, неверная сумма).

### 8.2 Статусы заказа

Допустимые переходы задаются в одном месте (`app/db/order_fsm.py`), любой другой переход — исключение:

- `created` → `analyzing` → `analyzed` (или `rejected` при невалидном файле)
- `analyzed` → `awaiting_payment` → `paid` (или `expired` / `canceled`; из них можно снова в `awaiting_payment`)
- `paid` → `processing` → `done`
- `processing` → `awaiting_user_input` → `processing`
- `processing` → `failed` → `refunded`
- `done` → `complaint` → `done` (после повторной обработки) или `refunded`

Для бета-пользователей переход `analyzed → paid` выполняется без платежа с событием `beta_free` в аудите.

## 9. Безопасность, приватность, хранение файлов

- **Сроки хранения** (в конфиге): неоплаченный анализ — файл удаляется через 2 часа; исходник и результат оплаченного заказа — через 24 часа после выдачи; файлы по жалобе с согласием пользователя — 14 дней. Удаление выполняет фоновая задача каждые 10 минут, удаление логируется в `events`. Те же сроки пропиши в политике.
- Файлы хранятся в отдельном томе с именами по UUID, без исходных имён на диске. Шифрование на диске — опционально (флаг), через Fernet с ключом из `.env`.
- **В логах нет текста документов**: только id заказов, id блоков, коды ошибок, метрики. Для отладки на корпусе — отдельный режим `DEBUG_TEXT_LOGS`, запрещённый в продакшене (проверка при старте).
- Обработка файла — только в worker с таймаутом (например, 120 с на документ) и лимитом памяти контейнера. LibreOffice запускается с отдельным профилем пользователя на каждый вызов, с таймаутом и без сети.
- Входные файлы — только .docx, проверка по содержимому (zip + `[Content_Types].xml`), а не по расширению. Отказ при макросах, внешних ссылках на шаблоны (`attachedTemplate` с URL удаляется), OLE-объектах с исполняемым содержимым.
- Webhook ЮKassa: проверка IP и обязательная сверка через API (раздел 7.2). Секреты только в `.env`, админ-команды только для `ADMIN_IDS`.
- Rate limit: 10 документов в час на пользователя, 30 сообщений в минуту. Бан пользователя через `/admin`.
- В ИИ уходят только фрагменты серой зоны без титульного листа, с маскированием контактов (раздел 5.3).
- Уведомления владельцу в Telegram: ошибки worker, `failed`, возвраты, жалобы, недоступность ЮKassa или ИИ, заканчивающееся место на диске.

Перед запуском проверить у юриста»**. Ты не юрист и не должен выдавать черновик за готовый документ.

**Публичная оферта** (договор оказания услуг):

**Политика обработки персональных данных** (152-ФЗ): какие данные обрабатываются (Telegram id, имя пользователя, email для чека, содержимое документа, включая данные с титульного листа), цели, правовые основания, сроки хранения (раздел 9), передача третьим лицам (ЮKassa — для оплаты и чеков; провайдер ИИ — фрагменты текста без титульного листа; хостинг), права субъекта и порядок отзыва согласия.

**Правила использования:** запрещённые материалы, лимиты, поведение бота при нарушениях, поддержка.

В README отдельным пунктом перечисли вопросы, которые владелец должен решить с юристом: требования 152-ФЗ к локализации данных и к трансграничной передаче (провайдер ИИ), уведомление Роскомнадзора об обработке ПДн, формулировки о возвратах с учётом закона о защите прав потребителей, настройки чеков по 54-ФЗ под налоговый режим ИП.

## 11. Тестирование и эталонный корпус

Качество продукта измеряется на корпусе, а не на ощущениях.

1. **Разметка корпуса.** Для каждого файла из `tests/corpus/raw/` сгенерируй черновую разметку типов блоков (`tests/corpus/annotated/<name>.json`) правилами, затем выведи для владельца удобный для проверки список (id, тип, первые слова). Владелец исправляет ошибки, и разметка становится эталоном. Не считай черновую разметку эталоном без подтверждения.
2. **Метрики** (`python -m app.core.cli eval`): точность классификации по типам и в целом, число элементов в серой зоне, доля ошибок, пойманных отчётом «Проверьте вручную». Цель: 0 ошибок среди элементов с уверенностью ≥ 0.90, проверка целостности — 100 % файлов, линтер — 0 ошибок уровня `error` на всех файлах корпуса.
3. **Unit-тесты** на каждое правило классификации, каждую нормализацию, каждое правило линтера, разрешение наследования стилей, перенос рисунков, формул, сносок и гиперссылок.
4. **Синтетические документы:** генератор кривых docx (отступы пробелами, жирный вместо заголовков, ручная нумерация, пустые абзацы, смешанные шрифты, альбомный раздел, вложенные таблицы) для регрессионных тестов.
5. **Визуальная проверка:** CLI-команда, которая рендерит исходник и результат в PDF и собирает их постранично рядом в один файл для просмотра глазами.
6. **Интеграционные тесты бота и оплаты** (раздел 7.4) с тестовым магазином ЮKassa и моками Telegram.
7. Каждая жалоба из бета-теста становится новым файлом корпуса и тестом.

CI: GitHub Actions с `ruff`, `mypy`, unit-тестами и прогоном корпуса (корпус хранится вне публичного репозитория).

## 12. Деплой и эксплуатация

- **Docker Compose**, сервисы: `bot` (aiogram, long polling), `api` (FastAPI: webhook ЮKassa, юридические страницы, `/health`), `worker` (arq + LibreOffice + шрифты), `postgres`, `redis`, `caddy` (автоматический HTTPS для домена webhook).
- Один VPS на старте (2 vCPU, 4 ГБ RAM достаточно). Где физически размещать сервер с учётом 152-ФЗ, решает владелец после консультации с юристом: вынеси это в README как открытый вопрос.
- `.env.example` со всеми переменными и комментариями: `BOT_TOKEN`, `ADMIN_IDS`, `DATABASE_URL`, `REDIS_URL`, `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_WEBHOOK_IPS`, `PUBLIC_BASE_URL`, `PRICE_RUB`, `RECEIPTS_ENABLED`, `RECEIPT_VAT_CODE`, `LLM_ENABLED`, `ANTHROPIC_API_KEY`, `LLM_MODEL`, `LLM_ESCALATION_MODEL`, `LLM_MAX_COST_PER_DOC_USD`, `BETA_MODE`, `RETENTION_*`, `IP_NAME`, `INN`, `OGRNIP`, `SUPPORT_CONTACT`, `TERMS_VERSION`.
- Миграции Alembic применяются при старте `api`.
- Ежедневный бэкап PostgreSQL (`pg_dump`) с хранением 14 дней. Файлы документов не бэкапятся.
- Логи в JSON в stdout. Опционально Sentry (`SENTRY_DSN`).
- README: установка с нуля на чистый Ubuntu, настройка webhook в личном кабинете ЮKassa, переключение тестовый → боевой магазин, добавление нового профиля вуза, обновление без простоя.
